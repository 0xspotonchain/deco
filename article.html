Don't trust — verify: what my agent actually did, with receipts

Entry by deco · Track: Creator Track · Season: 21 Oct – 21 Nov 2026 · Tags: #AgentGames @ZKVProtocol

My agent runs on a VM and moves money every morning — testnet money, but real transactions. This is what I built, what I tested, what landed, and what failed. All of it checked, none of it taken on faith.

“DYOR, don't trust — verify, not your keys, not your coins.”

Why that motto is the whole point

That line is not a slogan I put on a profile. It is the rule I run by. An agent that trades, signs and claims on your behalf is useful only if you do not have to take its word for anything. So when I set mine up, I built it the same way I would check anyone else's work: addresses you can look up, transaction hashes you can open, balances you can verify, and failures reported as plainly as successes.

Here is the build, in the order it happened.

First: a Circle agent wallet on Arc testnet

The first piece was a Circle agent wallet on Arc testnet — the wallet my agent uses for its daily claims.

Testnet tokens, yes. But the transactions are real, the wallet is real, and anyone can check both. That is the standard everything else in this entry is held to.

Then: one seed, five addresses

Next I built a multichain burner wallet: one seed, five addresses — Bitcoin SegWit, Bitcoin testnet4, EVM, Solana, and TRON.

It uses standard BIP44 derivation paths, so one backup restores all of them, and the wallet imports into Trust Wallet, MetaMask, Phantom, and TronLink. One seed to protect, one backup to keep, five chains covered. A burner is meant to be simple and disposable — if the setup needs a spreadsheet to survive, it is already wrong.

I didn't trust it — I tested it

A new wallet that holds five chains is exactly the kind of thing you do not take on trust. So before it touched a single faucet, I tested it.

8 out of 8 tests passed:

  • Sign-and-verify on EVM and Solana
  • Re-derivation checks on BTC and TRON
  • Decrypt round-trips on the encrypted backup
  • Every address live-checked on its explorer

Balances were 0 across the board — exactly as expected for a fresh wallet, and exactly what the explorers showed. If a test had failed, the wallet would not have been used. Fail closed, fix it, test again.

What failed — and why that matters more

Plenty did not land. I am putting the failures in the entry on purpose, because an agent report that only lists wins is marketing, not verification.

  • QuickNode: gated behind a mainnet balance, so it is unusable for a fresh burner wallet.
  • pk910: blocked my VM's hosting IP range, so the proof-of-work faucet cannot be claimed from the VM.
  • Solana public RPC airdrop: closed — it returns HTTP 410.
  • Helius: its devnet faucet is paid-only, not free. I checked instead of assuming.

Each failure has a specific, checked reason — not “it didn't work,” and not a quiet omission. When an agent hits a wall, the honest output is the wall, the reason, and what would have to change. Anything else teaches you to trust an agent that has not earned it.

That's the point: proof, not a promise

An agent that trades, signs and claims cannot just say it did the thing. A transaction hash, an explorer check, a daily balance verification — that is proof, not a promise.

That is why verifiable agents matter, and it is why my motto and this contest point in the same direction. Don't trust. Verify. Build the agent so that anyone — starting with you — can check its work without asking it nicely.

Still open, and what comes next

Two items are still open: Sepolia and Solana devnet. Both are blocked from the VM for the reasons above, so I will fund them from my own device instead of pretending the agent did it.

Next build: onchain sniper tools. Same rule applies there, only more so — the faster an agent moves, the more its work has to be checkable after the fact.
